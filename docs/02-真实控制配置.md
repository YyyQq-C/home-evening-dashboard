# 真实控制配置

## 先弄清两张页面

`index.html` 继续用于展示原暮色界面：模型、灯光、房间、场景和家电操作为模拟；可以配置真实只读数据。

`control.html` 是本次新增的实际服务调用入口。它没有复制原页面的假状态，不先把图标改成“成功”，而是把命令提交到当前 HA 会话，持续读取真实实体。刚解压时是 `read-only`，只有你明确修改为 `live` 才允许下发。

## 一份最小可用配置

将下例中的实体全部换成自己的实体后，写入 `www/home-evening/site-config.js`。没有的设备删除对应对象，不填假实体凑数。

```js
export const SITE = {
  control: {
    mode: 'read-only',
    timeoutMs: 15000,
    devices: [
      {key:'living_light', name:'客厅灯光', kind:'light', entity:'light.my_living_light'},
      {key:'living_ac', name:'客厅空调', kind:'climate', entity:'climate.my_living_ac', onMode:'cool'},
      {key:'living_floor', name:'客厅地暖', kind:'climate', entity:'climate.my_living_floor', onMode:'heat'},
      {key:'fresh', name:'全屋新风', kind:'fan', entity:'fan.my_fresh_air'}
    ],
    scenes: []
  },
  camera: {serial:''},
  weather: {sensors:{}},
  entities: {}
};
// 供原展示页读取显式配置的实体；不要删除这个导出。
export function entityId(alias) { return SITE.entities[alias] || ''; }
```

`key` 是当前配置里的唯一操作标识，不能重复。`name` 是给人看的名称，可以修改。`entity` 必须是自己 HA 中已存在的实体。`kind` 决定允许调用的服务类别，不接受任意服务名或任意目标。

`entities` 用于原展示页的数据绑定，`control.devices` 用于新增入口的实际控制，两者不是自动匹配。想让原房间卡片读同一台空调，再加：

```js
entities: {
  'climate.example_ac_living': 'climate.my_living_ac',
  'climate.example_floor_living': 'climate.my_living_floor'
}
```

不要在一个对象里重复定义两个 `entities`，把内容合并到已有对象即可。

## 灯光和继电器

`kind:'light'` 允许绑定 `light.xxx` 或用于开关灯的 `switch.xxx`。

绑定 `light` 时，开关发送 `light.turn_on` / `light.turn_off`；实体确实提供调光能力时，亮度发送 `light.turn_on`，参数为 `brightness_pct`。不支持调光的灯不会因为界面有输入框就获得调光能力。

绑定 `switch` 时只允许开关，不允许提交亮度。不要把童锁、排水、门锁之类的实体当灯光映射。

一次动作只针对该配置的一个实体。如果需要同时控制多路灯，先在 HA 建立灯组或场景，再显式配置；不要让前端通过名称猜测“客厅所有灯”。动作说明见 [HA Light 文档](https://www.home-assistant.io/integrations/light/)。

## 空调

支持的动作包括电源、设定温度、运行模式和设备风速。界面的模式与风速选项来自实体的 `hvac_modes`、`fan_modes`，提交原始英文值，不用中文标签作为 API 参数。

| 操作 | HA 服务 | 主要参数 |
| --- | --- | --- |
| 开机 | `climate.set_hvac_mode` | 关闭状态下使用自己配置的 `onMode` |
| 关机 | `climate.set_hvac_mode` | `hvac_mode: 'off'` |
| 调温 | `climate.set_temperature` | `temperature`，不夹带模式 |
| 改运行模式 | `climate.set_hvac_mode` | 实体实际支持的模式 |
| 改设备风速 | `climate.set_fan_mode` | 实体实际支持的 `fan_mode` |

为什么需要 `onMode`？设备关闭时，仅凭 `state:'off'` 无法决定开机要制冷还是制热。示例中的 `cool` 需要你自己确认，不适合的设备不要照抄。已经开启的设备点“开启”，保持它当前的有效模式，不另选一个模式。

温度输入按实体提供的 `min_temp`、`max_temp` 和 `target_temp_step` 校验。范围或步长缺失时，本入口禁用调温，避免给未知设备套一个固定范围。只读原生实体正常却缺少元数据时，先处理集成能力，而不是在前端强行补值。

例如下列调用说明的是协议内容，不会由文档自动执行：

```yaml
action: climate.set_temperature
target:
  entity_id: climate.my_living_ac
data:
  temperature: 25
```

该动作没有额外发送开机、制冷或风速设置。具体硬件如何响应仍取决于集成和设备。官方能力说明见 [HA Climate 文档](https://www.home-assistant.io/integrations/climate/)。

## 地暖

地暖同样使用 `kind:'climate'`，不是在前端创造一个“地暖协议”。控客集成创建的地暖实体与其他品牌温控器都可以按实际能力填写。

普通开关型地暖通常填写 `onMode:'heat'`，但必须在其 `hvac_modes` 中确实存在 `heat`。步长以实体为准，可能为 0.5°C。没有 `fan_modes` 的地暖会禁用风速选项，不下发空调风速服务。

把每个分区分别列入 `devices`，按实际房间核对。作者的原空调编号和地暖编号对应关系不同，项目已经移除了真实编号，不能拿示例数组顺序当作自己的接线表。

## 新风

实体应为 `fan.xxx`，`kind:'fan'`。开关调用 `fan.turn_on` / `fan.turn_off`，百分比调用 `fan.set_percentage`。只有实体提供百分比读数时才开放该输入；原厂档位与百分比的换算由后端集成负责。

控客三档在作者原环境里对应约 33/67/100%，用户仍应核对自己的实体和集成。`preset_modes` 非空时才显示可提交的预设值，不能给没有“自动”预设的设备自行发一个 `auto`。

有些集成在设置非零风速时会启动设备。本包不会附加另一条开机命令，但也不承诺“调风速绝不改变电源”。先观察自己的原生卡片行为。见 [HA Fan 文档](https://www.home-assistant.io/integrations/fan/)。

## 回家、离家和睡眠

真正的场景放在 HA 后端管理。前端只绑定你已经验证过的 `scene` 或 `script`，不把展示页里的模拟场景批量翻译成设备命令。

```js
scenes: [
  {key:'home', name:'回家', entity:'scene.my_home'},
  {key:'leave', name:'离家', entity:'script.my_leave'}
]
```

`configs/scripts.example.yaml` 提供一个离家脚本的结构。先逐项替换实体，再把脚本合并进自己的 `scripts.yaml`，检查并重载脚本后确认真实实体 ID，最后配置前端。场景服务返回不表示每台设备都完成了动作；脚本中途失败也可能已经执行了一部分操作。

## 状态、超时与刷新

按钮提交以后显示“HA 已受理”，卡片读数继续从实体回读，不立即改成本地期望状态。控客的原厂缓存默认约 30 秒轮询，所以服务受理与界面读数改变可能有时间差。

15 秒是服务响应等待时间，不是设备物理升温完成时间。超时显示“执行结果未知”，先看实体和设备，不能把超时等同于未执行并不停重试。同一设备等待响应期间阻止重复提交；不同设备彼此隔离。

断线、缺失实体、`unknown`、`unavailable` 都拒绝下发。前端不保存令牌，实际权限仍由当前 HA 用户及后端控制；配置白名单只是限制这张页面的行为，不是 HA 的权限隔离机制。

## 验证顺序

1. 在原生 HA 里确认一个准确实体及其动作。
2. 只读模式核对读数、上下限和可选项。
3. 改为 `live` 后，自己观察一台设备，完成单次动作。
4. 同时检查服务结果、实体回读和物理设备，三项分别记录。
5. 再测设备断线、重复点击、刷新、温度草稿和返回页面。
6. 单设备稳定以后，才绑定 HA 场景或脚本。

## 后续把原模型按钮也接上，应该改哪里

这一步未在本包自动完成。原展示页有三条不同操作路径，不能只在 `saveState()` 上加请求，也不能通过比较整份状态来判断应该控制哪台设备。

- `app.js` 的 `toggleState()` 同时被房间按钮、2D 标记和 3D 消息调用，应统一接入一个明确的设备动作入口。
- 温度经 `editTemperature()` 的草稿计时器处理；要改成每台设备独立防抖的真实服务提交，回读更新不能覆盖尚未提交的草稿。
- `climate-dialog.js` 的电源、模式和风速有独立事件分支，目前直接修改模拟对象，必须逐项改为明确调用。
- `onClick()` 的 `scene`、`speed`、`fresh-mode` 和家电分支也要分别处理。场景应指向 HA 场景或脚本，家电不应通过通用猜测控制。
- `model-adapter.js` 只收发几何标记的消息。保留来源与 origin 校验，不能让消息直接指定任意 HA 服务或实体。

可以复用本包 `control-actions.js` 的白名单和校验逻辑，但还需要重做展示页的 pending、失败提示、真实状态回读和全部入口的回归。原展示页里的“已模拟执行”文案也必须同步调整。完成这些工作以前，应保留“模拟”标记，而不是让用户把模型动画当作真实控制成功。
